# Sellora V2.1 — Bulk Product Import Specification

**Status:** Proposed for review  
**Target branch:** `develop`  
**Scope:** CSV + XLSX product import; create-only and preview-based update modes.  
**Out of scope:** Razorpay/payment changes, multi-business switching, bulk image ZIP uploads, and changes to the legacy yarn-specific `Product` model.

## 1. Goals

Let an authenticated business owner create or update generic `SelloraProduct` records in bulk, with a safe preview, row-level validation, duplicate detection, and a downloadable error report.

Initial limits (configurable): 5 MB per file and 1,000 data rows per import. Imports exceeding limits must be rejected with a clear message.

## 2. Product template

CSV and XLSX templates should include:

| Column | Rule | Destination |
|---|---|---|
| `name` | Required | `SelloraProduct.name` |
| `sku` | Optional; unique within a business when provided | `SelloraProduct.sku` |
| `description` | Optional | `SelloraProduct.description` |
| `price` | Optional for enquiry-led products; otherwise non-negative decimal | `SelloraProduct.price` |
| `currency` | Default `INR`; ISO currency code | `SelloraProduct.currency` |
| `unit` | Default `piece` | `SelloraProduct.unit` |
| `imageUrl` | Optional HTTP(S) URL | `SelloraProduct.imageUrl` |
| `stockEnabled` | Default `false` | `SelloraProduct.stockEnabled` |
| `stockQuantity` | Non-negative decimal when stock is enabled | `SelloraProduct.stockQuantity` |
| `isActive` | Default `true` for new products | `SelloraProduct.isActive` |
| `fields` | Optional JSON/custom attributes validated against business field definitions | `SelloraProduct.fields` |

Provide an optional yarn-textiles example template with yarn count, yarn type, shade/colour, composition, and minimum order quantity in `fields`. These attributes must not be mandatory for other industries.

## 3. Import modes and matching

- **Create new:** never overwrite existing products. A SKU already in use in the current business is a row error.
- **Update existing:** match on normalized SKU within the authenticated business. Preview before/after values and require explicit commit.
- Empty SKU values are allowed. Products without SKUs cannot be matched for update.
- Trim SKU whitespace and use case-insensitive matching for duplicate detection. Define and consistently apply a canonical SKU format.
- Duplicate non-empty SKUs within the uploaded file invalidate all conflicting rows; never choose a winner implicitly.
- In update mode, unmatched SKUs are shown as proposed creates and require explicit confirmation.
- Only mapped fields may change. Blank cells preserve current values by default; clearing a field must be an explicit option.
- Revalidate at commit time and reject stale previews if the underlying matched product changed since preview.
- Never read or mutate another business's products. Do not accept a client-supplied business ID as authorization.

## 4. Proposed data model

Add `ProductImportJob` and `ProductImportRow` to Prisma after checking the live schema and migration history.

### ProductImportJob

- `id`, `businessId`, `createdByUserId`
- `fileName`, `fileType`, `mode`
- `status`: `UPLOADED`, `VALIDATING`, `READY`, `PROCESSING`, `COMPLETED`, `COMPLETED_WITH_ERRORS`, `FAILED`, `CANCELLED`
- `totalRows`, `validRows`, `invalidRows`, `createdRows`, `updatedRows`, `skippedRows`
- `createdAt`, `updatedAt`, `completedAt`

### ProductImportRow

- `id`, `jobId`, `rowNumber`
- `rawData` JSON, `normalizedData` JSON
- `action`: `CREATE`, `UPDATE`, `SKIP`, `INVALID`
- `matchedProductId` nullable, `errors` JSON, `warnings` JSON, `appliedAt`
- timestamps

Add indexes for business/job listing and row paging. Uploaded files should be temporary; do not retain original files indefinitely. Apply the project's retention and privacy policy.

### SKU uniqueness

The current generic product schema has nullable `sku` and no business-scoped unique constraint. Add a PostgreSQL-compatible unique constraint on `(businessId, sku)` after auditing existing data and duplicates. PostgreSQL permits multiple NULL values in a standard unique index. If case-insensitive uniqueness is required, normalize SKU on write or use a carefully reviewed expression index; Prisma schema representation and migration SQL must remain consistent.

## 5. Proposed API contract

All routes require existing authentication and derive the business from the authenticated user.

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/workspace/products/import/template?format=csv` | Download CSV template |
| GET | `/api/workspace/products/import/template?format=xlsx` | Download XLSX template |
| POST | `/api/workspace/products/imports` | Upload file and create job |
| GET | `/api/workspace/products/imports/:jobId` | Job status and totals |
| GET | `/api/workspace/products/imports/:jobId/rows?page=1&pageSize=50` | Paginated preview/errors |
| PATCH | `/api/workspace/products/imports/:jobId/mapping` | Save column mapping |
| POST | `/api/workspace/products/imports/:jobId/validate` | Validate and generate preview |
| POST | `/api/workspace/products/imports/:jobId/commit` | Commit the confirmed preview |
| POST | `/api/workspace/products/imports/:jobId/cancel` | Cancel before commit |
| GET | `/api/workspace/products/imports/:jobId/errors.csv` | Download row error report |

These are proposed paths; reconcile with existing routes before implementation. Use consistent Zod validation and JSON errors. Suggested responses: 201 for job creation, 202 for queued processing, 400 for invalid input, 401 for no session, 403 for unauthorized business access, and 404 for unknown/inaccessible jobs.

Commit must be idempotent. Use a preview version/checksum to prevent applying stale changes. Process bounded batches outside the request-response cycle. Use transactions and database uniqueness constraints as final safeguards. Stock changes must follow existing stock-movement rules; do not silently overwrite stock without an audit record.

## 6. File handling and security

- Accept only CSV and XLSX; enforce extension, MIME/content validation, size and row limits.
- Use a maintained XLSX parser. Do not execute formulas or macros; treat imported values as data.
- Reject malformed archives and pathological spreadsheets safely.
- Validate all fields server-side, including custom fields against `Business.catalogueFields`.
- Validate image URLs as HTTP(S), but do not fetch them during import.
- Keep uploads temporary and clean up after processing/expiry.
- Never expose raw database exceptions, filesystem paths, tokens, or secrets in API errors.
- Add rate limits and request correlation IDs to upload/validation/commit routes.

## 7. Acceptance criteria

- [ ] CSV and XLSX templates download and open correctly.
- [ ] Valid files parse without changing existing product data before commit.
- [ ] Empty/malformed/oversized files are rejected safely.
- [ ] Invalid names, prices, stock and custom fields show row-specific errors.
- [ ] Duplicate SKUs in the upload and conflicts with existing products are detected.
- [ ] Create-only mode never overwrites a product.
- [ ] Update mode displays before/after values and requires confirmation.
- [ ] Blank cells preserve existing values unless the user explicitly chooses clear.
- [ ] No product changes occur before commit.
- [ ] Repeated commit requests do not duplicate records.
- [ ] Concurrent updates/SKU conflicts are handled safely.
- [ ] Product changes remain scoped to the authenticated business.
- [ ] Stock changes create the appropriate `SelloraStockMovement` audit records.
- [ ] A downloadable error report contains row numbers and actionable messages.
- [ ] 1,000-row imports meet the agreed performance target.
- [ ] Existing product, catalogue, enquiry, stock and order flows continue to work.

## 8. Test checklist

### Build and migration
- [ ] API TypeScript build and Prisma generation pass.
- [ ] Migration applies to a clean test database.
- [ ] Migration applies to a copy of the existing schema without data loss.
- [ ] Existing duplicate SKUs are audited before adding uniqueness.

### Import behaviour
- [ ] CSV happy path and XLSX happy path.
- [ ] Wrong extension, invalid MIME, malformed CSV/XLSX, empty file, 5 MB+ file, and >1,000 data rows.
- [ ] Missing required field, invalid decimal, negative stock, invalid URL and invalid custom field.
- [ ] Duplicate SKU inside file, SKU already in database, case/whitespace variants, and blank SKU.
- [ ] Create-only mode against an existing SKU.
- [ ] Update preview, explicit field clearing, stale preview and concurrent update.
- [ ] Commit retry, batch failure and partial row errors.
- [ ] Cross-business access attempts for job, rows, commit and error report.
- [ ] Stock movement audit and existing product CRUD regression.
- [ ] Performance test with 1,000 rows.

## 9. Delivery sequence

1. Review current product CRUD, business authorization, upload configuration, dependencies, and migration history.
2. Add the migration and import job models.
3. Implement safe template generation and CSV/XLSX parsing.
4. Implement row validation, SKU matching, preview and stale-preview protection.
5. Implement idempotent commit, bounded processing and error export.
6. Add Products UI for import mode, mapping, preview, progress, and results.
7. Add automated tests and update the test guide.
8. Run build and tests, deploy to a preview environment, and verify before merging to `develop`.
